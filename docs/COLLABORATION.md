# 团队协作与候选作品选择

每人独立克隆、Key、账本、研究项目；共享经过测试的框架和公开协议。当前仓库公开，协作者邀请由仓库拥有者在 Settings 中配置。

- `main`：可交接的稳定代码。
- `feature/<member>-<topic>`：框架开发，测试后提 PR。
- 科研开始时记录 `git rev-parse HEAD`，运行过程中不要拉取代码或修改模型配置；修改了实验方法应新建协议，不能覆盖已完成的记录。
- 合并前运行 `python -m pytest -q`。暂存后运行 `python scripts/check_share.py`，它扫描 Git 索引而非仅扫描当前磁盘内容。
- GitHub Actions 只执行离线测试和公开依赖下载，不配置模型 Key，也不启动收费科研。

## 五人安排建议

一人负责框架、预算登记和最终提交；另外四人分成两条研究线，每条两人相互审查。不同研究线可以共用框架，但分别冻结协议与主要指标。不要五个人反复生成同一实验的不同措辞来挑评审分数。

## 团队预算

个人配置中的上限是本机额度，不是全队集中配额。队长从团队总授权中扣除已有报告消耗和未结算预留后分配成员配额；各成员额度之和不得超过剩余额度。不同模型/供应商 Token 的计费口径需另行核对。模型 Key 不等于免费额度。

每次候选交接附各模型报告消耗、保留预留、请求数、失败数和运行时长。保留账本，不以新克隆、新别名或换配置清零。外部监督工具的用量另记。

## 选优及提交

候选记录见 `candidate-template.json`。先看合规、复现、证据与论文本身，再参考 Agentic Reviewer；其估分不是比赛总分。只对实质不同且已完成审查的候选申请评审，保留全部评审结果。

按 2026-10-01 核对的[赛题规则](https://www.xir.cn/competition/1167/dataware)，每日每队最多提交 3 次，每个周期以最后一次提交为准；五轮间才取最高成绩。因此由队长统一提交选定候选，组员不各自覆盖平台作品。临近提交须重新核对官网。
